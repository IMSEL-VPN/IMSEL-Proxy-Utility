# Директивы отдельного сервера

Провайдер может передать настройки **одного сервера** в его имени (remark).
Это не HTTP-заголовки и не команды для всей подписки: соседние серверы,
другие подписки и настройки приложения не меняются.

## Где размещать

Добавьте директивы в квадратных скобках к имени сервера:

```text
Germany [nodeid=eu-de-01] [mux=on-tcp=8-udp=16-quic=skip]
```

Для ссылок директивы читаются из декодированного имени. В обычной ссылке
это имя после `#`, в VMess это `ps`. Кодируйте имя по правилам формата
ссылки: в URL используйте процентное кодирование, а не необработанные
пробелы и скобки. Для готового JSON метки размещаются в `remarks`, но
настройки подключения ограничены отдельными правилами ниже.

- Имена команд и текстовые ключи регистронезависимы: `[MUX=OFF]` и
  `[mux=off]` означают одно и то же. Регистр Base64-данных менять нельзя.
- Распознанные директивы скрываются из отображаемого имени, даже если их
  значение некорректно. Например, `[mux=invalid]` не становится частью названия.
- Неизвестные метки остаются обычным текстом: `[Premium]` не скрывается
  и ничего не включает.
- Конфликтующие повторы отменяют только соответствующую команду.
  Например, `[mux=on-tcp=8-udp=16-quic=skip] [mux=off]` не выбирает
  случайно первое или последнее значение MUX; другие корректные команды
  того же сервера продолжают действовать.
- Одинаковые повторы допустимы. Некорректный повтор также отменяет всю
  соответствующую команду: корректная метка не перекрывает ошибочную.
- Некорректная команда не включает настройку и не отменяет остальные
  корректные команды.

Исходная ссылка или JSON сохраняется. Скрытие меток в списке **не является
шифрованием**: они могут быть видны в исходной конфигурации, экспорте или
другом совместимом клиенте. Не помещайте в них секреты.

## Приоритет и обновление

Для сервера из ссылки корректная директива задаёт собственное значение
соответствующей настройки. Явное `off` или `0` также является значением,
а не отсутствием команды. Остальные параметры работают обычным образом.
Ограничения совместимости протокола и транспорта сохраняются.

Сервер без директив использует обычные настройки. При успешном обновлении
подписки действуют директивы из **новой версии имени**: если метка исчезла,
её прежнее значение больше не применяется. Это отличается от настроек
подписки через HTTP-заголовки, где отсутствие заголовка обычно сохраняет
ранее полученный выбор.

Пример: сервер A с `[mux=off]` не использует MUX, даже если он включён для
группы. Сервер B без этой директивы продолжает использовать обычные настройки
группы. Удаление `[mux=off]` у A при следующем успешном обновлении возвращает
обычное поведение A, не меняя B.

## MUX

```text
[mux=on-tcp=8-udp=16-quic=skip]
[mux=off]
```

`tcp` задаёт параллельность TCP, `udp` параллельность UDP. Оба принимают
целые числа **от 1 до 1024**. Значения `0`, отрицательные числа и числа
вне диапазона недопустимы.

Параметр `quic` управляет обработкой UDP на порту 443:

| Значение | Действие |
| --- | --- |
| `skip` | Передавать такой трафик без MUX |
| `reject` | Отклонять такой трафик |
| `allow` | Разрешить его передачу через MUX |

`[mux=off]` явно выключает MUX только для этого сервера. Включение не делает
MUX совместимым с протоколом или транспортом, который его не поддерживает.

## Проверка сертификата

```text
[allowinsecure=1]
[allowinsecure=0]
```

Для сервера из ссылки `1` **отключает проверку сертификата**, а `0`
возвращает её. Это собственное переопределение только для указанного сервера.
Также принимаются `true` вместо `1` и `false` вместо `0`.
`allowinsecure=1` не означает «безопасный режим»: используйте его только при
осознанном доверии провайдеру. Непроверенное соединение допускает подмену
сервера и перехват данных.

Отдельное исключение совместимости сохраняется для Hysteria2: в текущей
версии приложения проверка сертификата для него пропускается независимо
от этой директивы, в том числе при `allowinsecure=0`. Не рассчитывайте на
эту метку как на способ включить строгую проверку Hysteria2. Для остальных
протоколов это исключение не действует.

## Фрагментация

```text
[fragment=on-packets=tlshello-length=100:200-interval=10:20]
[fragment=off]
```

`packets` выбирает пакеты для фрагментации, `length` задаёт длину фрагмента,
`interval` интервал между фрагментами в миллисекундах. В примере
фрагментируется TLS ClientHello, длина составляет от 100 до 200 байт,
интервал от 10 до 20 мс.

| Параметр | Допустимые значения |
| --- | --- |
| `packets` | `tlshello`, номер пакета или диапазон номеров от `1` до `65535`, например `1:3` |
| `length` | Длина от `1` до `65535` байт |
| `interval` | Интервал от `0` до `60000` мс |

**Разделитель границ диапазона здесь двоеточие:** `100:200`, не `100-200`.
Дефис разделяет параметры самой директивы. Нижняя граница не должна быть
больше верхней. `[fragment=off]` явно выключает фрагментацию этого сервера.
Применимость зависит от типа соединения.

## Шумовые пакеты

```text
[noise=on-type=rand-packet=10:20-delay=10:16]
[noise=off]
```

В примере `rand` означает случайное содержимое, `packet=10:20` длину
пакета от 10 до 20 байт, `delay=10:16` задержку от 10 до 16 мс.
Диапазоны также разделяются двоеточием, нижняя граница не больше верхней.
`[noise=off]` явно выключает шум для этого сервера. Директива применяется
только к совместимым соединениям.

| Параметр | Допустимые значения |
| --- | --- |
| `type` | `rand`, `str`, `hex`, `base64` |
| `packet` для `rand` | Длина от `1` до `65535` байт |
| `packet` для `str` | Текстовое содержимое, не более 16 КиБ в UTF-8 |
| `packet` для `hex` | Корректное шестнадцатеричное содержимое, после декодирования не более 16 КиБ |
| `packet` для `base64` | Корректное Base64-содержимое, после декодирования не более 16 КиБ |
| `delay` | Задержка от `0` до `60000` мс |

Для `str`, `hex` и `base64` обязательно укажите `packet`: команда без него
не применяется. Для `rand` можно опустить `packet`; числовой `packet` без
указания типа также означает `rand`. В текстовом содержимом избегайте
квадратных скобок и последовательностей вида `-ключ=`, которые служат
разделителями директивы.

## Sniffing

```text
[sniffing=on-routeonly=1-metadataonly=0]
[sniffing=off]
```

`routeonly=1` ограничивает использование распознанного имени маршрутизацией,
не подменяя адрес назначения. `metadataonly=1` ограничивает анализ
метаданными. Значение `0` выключает соответствующее ограничение.
`[sniffing=off]` явно выключает Sniffing для этого сервера.
Для `routeonly` и `metadataonly` также принимаются `true`/`false` вместо
`1`/`0`. Переключатели самих команд `mux`, `fragment`, `noise` и `sniffing`
записываются как `on`/`off`.

### Списки Sniffing

```text
[sniffdest=WyJodHRwIiwidGxzIl0=]
[sniffexclude=WyJleGFtcGxlLm9yZyJd]
```

Значение каждой команды это **Base64 от UTF-8 JSON-массива строк**, без
префикса `base64:`. В первом примере закодировано `["http","tls"]`,
во втором `["example.org"]`. Это не строка с элементами через запятую.

Принимаются обычный и URL-safe Base64, с завершающими `=` или без них.
После декодирования допускается не более **16 КиБ** корректного UTF-8 JSON,
не более **256 строк** в списке и не более **1024 символов** в одной строке.

`sniffdest` задаёт точный список типов распознавания (`destOverride`).
Поддерживаемые значения: `http`, `tls`, `quic`, `fakedns`, `fakedns+others`.
Явно переданный список используется точно: `fakedns` не добавляется
автоматически. Если собственного списка нет, действует обычный выбор,
включая `http`/`tls` и дополнительно `fakedns` при включённом FakeDNS профиля.

`sniffexclude` задаёт доменные исключения (`domainsExcluded`). Используйте
точные домены или записи с префиксом `regexp:` и непустым выражением.
Префиксы `domain:` и `geosite:` для этих исключений не поддерживаются.
Не передавайте пустые строки или управляющие символы.

Отсутствие команды означает отсутствие собственного списка. Чтобы явно
передать **пустой** список, закодируйте `[]`:

```text
[sniffdest=W10=]
[sniffexclude=W10=]
```

Отсутствие и `[]` не взаимозаменяемы. Для готового JSON отсутствие списка
сохраняет соответствующее значение JSON, а явно пустой список очищает его
только при разрешённом применении Sniffing к JSON.

## Информационная строка

```text
Service information [infoserv]
Maintenance [infoserv=announce=VGVjaG5pY2FsIHdvcmtz]
```

`[infoserv]` превращает запись в информационную строку, а не сервер для
подключения. Её заголовок это имя после удаления распознанных меток.
Форма `announce=BASE64` дополнительно передаёт объявление: обычный текст
UTF-8 в Base64 без префикса `base64:`. Пример содержит `Technical works`.
Объявление не является HTML, ссылкой для загрузки или командой.
Допускается обычный или URL-safe Base64 с завершающими `=` или без них;
декодированный текст должен быть корректным UTF-8 размером не более **16 КиБ**.

Информационную строку нельзя выбрать для подключения, проверить пингом,
использовать для автоподключения, выбора самого быстрого сервера или добавить
в сборку соединения. Ошибка Base64 или текста объявления **не возвращает
ей возможность подключения**.
При конфликтующих объявлениях текст объявления не применяется, но запись
остаётся информационной.

В первой версии передавайте такую запись как **валидную поддерживаемую
серверную ссылку** с меткой в имени. Отдельный текст вместо ссылки сервером
не становится. Положение в списке не имеет значения: первая строка без
`[infoserv]` остаётся обычным сервером, а информационная может быть любой
по счёту.

## Стабильный идентификатор

```text
Germany [nodeid=eu-de-01]
```

`nodeid` обозначает один сервер **в пределах одной подписки**. Сохраняйте
его при переименовании сервера и не переиспользуйте для другого сервера.
Одинаковое значение в разных подписках не объединяет записи.

Допустимы **от 1 до 128 ASCII-символов**: латинские буквы `A-Z`/`a-z`,
цифры `0-9`, точка, подчёркивание, двоеточие и дефис (`[A-Za-z0-9._:-]`).
Пробелы и другие символы недопустимы. Регистр самого ID сохраняйте неизменным.

Не назначайте один `nodeid` нескольким серверам той же подписки. Такое
совпадение неоднозначно: приложение не должно молча считать одну из записей
прежним сервером только по этому ID. Без `nodeid` обычный импорт и выбор
серверов продолжают работать.

## Готовый JSON

Метки в `remarks` не дают разрешение переписывать настройки готового JSON:

- `[infoserv]` и `[nodeid=...]` описывают роль записи и её идентификатор.
- MUX, фрагментация, шум и проверка сертификата удалённого готового JSON
  не переопределяются этими директивами.
- Sniffing и его списки применяются к готовому JSON только при собственном
  разрешении пользователя **«Применять настройки к JSON»** в настройках
  Sniffing именно этой группы. По умолчанию оно выключено, в том числе для
  URL-подписок. Директива не включает разрешение.
- Разрешение MUX, фрагментации и шума для локальной группы является отдельным
  выбором пользователя. Оно не открывает изменение TLS или Sniffing и не
  распространяется на JSON удалённых подписок.

Исходный JSON, его маршруты и посторонние поля не перезаписываются из-за
этих меток. Указанное выше исключение совместимости Hysteria2 сохраняется.
Подробнее о настройках группы: [Sniffing и списки](../faq/getting-started.md#6-сниффинг-и-списки-для-одной-группы).

## Проверка перед выдачей подписки

1. Передайте две обычные записи A/B, добавив директиву только в имя A.
2. Убедитесь, что отображаемое имя A очищено от известных директив, а
   произвольная метка `[Premium]` остаётся видимой.
3. Проверьте включение и явное выключение настройки у A. B не должен
   получать значение A.
4. Обновите подписку без директивы у A и проверьте возврат обычного поведения.
5. Добавьте информационную запись не первой строкой и убедитесь, что она
   не участвует в подключении, пинге и автоматическом выборе.
6. Сохраняйте уникальный `nodeid` при переименовании. Не выдавайте дубликаты
   в одной подписке и не рассчитывайте на случайный выбор при конфликте.

Команды для всей подписки описаны отдельно: [Управление приложением](app-management.md).
